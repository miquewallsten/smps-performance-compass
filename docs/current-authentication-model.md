# Current Authentication Model — SMPS Performance Compass

## Overview

SMPS uses a custom authentication system built on JWT tokens, bcrypt password hashing, and a security-question-based password reset mechanism. There is no email-based password reset, no account activation flow, and no MFA.

---

## Login Flow

**Endpoint**: `POST /api/auth/login`

1. User submits `{ email, password }`
2. Server queries `users` table by email
3. If user not found → `401 Invalid credentials` (does NOT reveal whether email exists)
4. If user found but `is_active = 0` → `403 Account is deactivated`
5. Password verified with `bcrypt.compare(password, password_hash)` (12 rounds)
6. JWT payload constructed:
   ```typescript
   {
     sub: user.id,
     email: user.email,
     role: getRole(user),  // 'super_user' | 'admin' | 'user'
     name: user.name,
     position: user.position,
     isManagingPartner: boolean
   }
   ```
7. JWT signed with `JWT_SECRET` from env, expires in 24h
8. Response: `{ token, user: sanitizeUser(user) }`
9. Frontend stores token in localStorage, sets Authorization header

**Role Derivation** (from `getRole` in `server/auth/jwt.ts`):
- `is_super_user = 1` → `super_user`
- `is_admin = 1 OR is_managing_partner = 1` → `admin`
- Otherwise → `user`

---

## Logout Flow

**Endpoint**: `POST /api/auth/logout` (requires authentication)

1. Token is extracted from Authorization header
2. Token is SHA-256 hashed
3. Hash is stored in `sessions` table with `user_id`, `created_at`, `expires_at`
4. All expired sessions are deleted (cleanup on every logout)
5. Frontend removes token from localStorage

**Session blocklist**: On every authenticated request, `authMiddleware` checks if the token hash exists in `sessions` table. If found, the request is rejected with `401 Token revoked`.

---

## Password Storage

- **Algorithm**: bcrypt, 12 rounds
- **Implementation**: `bcryptjs` npm package (pure JS, not native)
- **Location**: `server/auth/security.ts`
- **Salt**: Auto-generated by bcrypt per hash
- **Verification**: `bcrypt.compare(plaintext, hash)`
- **Minimum length**: 6 characters (enforced by Zod schema on change/reset)
- **No complexity requirements**: No uppercase, number, or special character rules

---

## Security Questions (Current Password Reset)

**Mechanism**: Every user has a `security_question` and `security_answer` stored in the `users` table.

**Reset Flow** (`POST /api/auth/reset-password`):
1. User submits `{ email, securityAnswer, newPassword }`
2. Server looks up user by email
3. If user not found → `404 User not found` (**leaks whether email exists**)
4. Security answer is normalized (lowercase, trim, collapse whitespace) and compared with `bcrypt.compare`
5. If answer matches → password is reset to `newPassword` (hashed with bcrypt)
6. `must_change_password` is set to 0

**Critical Weaknesses**:
- All seed users have the same security question: "¿Cuál es su correo electrónico?" with answer = their email
- The `reset-passwords.ts` script explicitly sets `security_question = '¿Cuál es su correo electrónico?'` and `security_answer = hash(email)`
- Admin-created users also default to `security_question = '¿Cuál es su correo electrónico?'` and `security_answer = hash(email)`
- This means anyone who knows an email address can reset that user's password — the answer IS the email
- The `POST /api/auth/security-question` endpoint reveals the security question type for any email, confirming the account exists

---

## Force Password Change

**Mechanism**: `users.must_change_password` column (TINYINT(1))

- When a user is created (by admin or system init), `must_change_password` is set to `1`
- When `must_change_password = 1`, the frontend redirects to `/change-password` instead of dashboard
- The `POST /api/auth/change-password` endpoint allows changing password without providing `currentPassword` when `must_change_password = 1`
- After successful change, `must_change_password` is set to `0`
- Admin password resets (`POST /api/users/:id/reset-password`) set `must_change_password = 1`

**Weakness**: The force-change flow also requires setting a security question and answer. If the user doesn't set a strong one, they remain vulnerable.

## User Creation (Current)

### System Init (SuperAdmin)
**Endpoint**: `POST /api/system/init` (unauthenticated, only works when system is not initialized)

1. Admin provides `{ name, email, password, securityQuestion, securityAnswer }`
2. Creates super_user with all flags: `is_admin=1, is_super_user=1, is_managing_partner=1, is_active=1, must_change_password=0`
3. Seeds work areas, positions, vacation config, module config

### Admin Creates User
**Endpoint**: `POST /api/users` (requires admin)

1. Admin provides `{ name, email, position, password, practiceArea?, customPositionId?, locationId?, isAdmin?, isManagingPartner? }`
2. **Admin sets the password** — this is a shared-secret problem
3. Security question is hardcoded: `'¿Cuál es su correo electrónico?'`
4. Security answer is the user's email address (lowercase, trimmed, hashed with bcrypt)
5. `must_change_password` is set to `1`
6. User must change password on first login

**Problem**: Admin knows the initial password. User has no way to set their own password privately.

### Copilot Creates User
The copilot `users` tool follows the same pattern — it requires a `password` field and sets the same hardcoded security question/answer.

## Token & Session Handling

| Property | Value |
|----------|-------|
| Token type | JWT (JSON Web Token) |
| Signing algorithm | HS256 |
| Token expiry | 24 hours |
| Token storage | Client-side localStorage |
| Token transport | Authorization: Bearer header |
| Token revocation | Blocklist in `sessions` table |
| Revocation check | Every authenticated request queries DB |
| Session cleanup | On logout only (expired sessions deleted) |

**JWT Payload**:
```json
{
  "sub": "uuid",
  "email": "user@example.com",
  "role": "super_user | admin | user",
  "name": "Full Name",
  "position": "asociado_sr",
  "isManagingPartner": false,
  "iat": 1234567890,
  "exp": 1234567890
}
```

**Session Table**:
```sql
sessions (
  id VARCHAR(36) PRIMARY KEY,
  user_id VARCHAR(36) NOT NULL,
  token_hash VARCHAR(255) NOT NULL UNIQUE,
  created_at DATETIME NOT NULL,
  expires_at DATETIME NOT NULL
)
```

**Weaknesses**:
- No idle timeout — token is valid for full 24h regardless of activity
- No refresh token mechanism — user must re-login after 24h
- Session cleanup only happens on logout calls, not on a schedule (40 stale sessions found in production audit)
- Token blocklist requires a DB query on every authenticated request (performance concern at scale)

## Auth Middleware Chain

```
Request → rate limiter → authMiddleware (JWT verify + blocklist check) → route handler
```

For admin routes:
```
Request → rate limiter → authMiddleware → requireAdmin → route handler
```

For self-or-admin routes:
```
Request → rate limiter → authMiddleware → requireSelfOrAdmin → route handler
```

---

## Rate Limiting

| Endpoint | Window | Max Requests |
|----------|--------|-------------|
| `/api/auth/login` | 1 minute | 5 (failed only) |
| `/api/auth/reset-password` | 15 minutes | 3 |
| `/api/auth/security-question` | 15 minutes | 3 (same limiter) |
| All other `/api/` | 1 minute | 100 |

## Identified Vulnerabilities

1. **Security questions are effectively public knowledge** — all users default to "¿Cuál es su correo electrónico?" with the answer being their email
2. **No email-based verification** — no way to verify email ownership
3. **No activation flow** — admin sets password, no token-based activation
4. **No MFA** — single factor authentication only
5. **No password complexity rules** — minimum 6 characters, no other requirements
6. **No account lockout** — only rate limiting (5 failed attempts per minute)
7. **Email enumeration** — `POST /api/auth/security-question` reveals if an email exists (returns question or null); `POST /api/auth/reset-password` returns 404 for unknown emails (vs 401 for wrong answer)
8. **No audit trail** — authentication events (login, logout, password change, reset) are not logged to `user_timeline` or any audit table
9. **Admin knows initial passwords** — no self-service onboarding
10. **Token blocklist scales poorly** — every request requires a DB query to check if token is revoked
